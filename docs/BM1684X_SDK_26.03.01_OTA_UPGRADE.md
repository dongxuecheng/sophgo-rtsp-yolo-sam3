# BM1684X SoC 在线升级 SDK v26.03.01

本文记录一台 BM1684X SoC 算法盒子从 `SophonSDK v23.09 LTS-SP5` 在线升级到 `SophonSDK v26.03.01` 的完整实测过程，供同型号设备复用。

本流程不需要 TF 卡，通过当前 Linux 系统执行官方 `ota_update.sh`。升级会改写启动固件、内核和系统分区，必须使用稳定电源，并提前把备份复制到另一台机器。

> **高风险提示**
>
> - `LAST_PART_NOT_FLASH=0` 会清空并重建 `/data`。
> - 只有在异机备份完成且校验通过后，才能使用该参数。
> - OTA 开始后不要重复执行、不要手动重启、不要断电。
> - 不要通过手工修改 `gpt.gz` 绕过分区检查；没有 TF 卡或串口恢复条件时风险尤其高。

## 2. 升级流程概览

```text
核对芯片和磁盘
    -> 备份系统配置及 /data
    -> 把备份复制到异机并校验
    -> 提取、传输 sdcard.tgz
    -> 校验包内全部文件
    -> 判断是否能保留 /data
    -> 启动后台 OTA
    -> Linux 阶段暂存升级包
    -> 自动重启
    -> U-Boot 阶段刷写固件和分区
    -> 再次启动并验证版本
```

## 3. 升级前检查

### 3.1 确认芯片与当前版本

```bash
uname -a
uname -m
cat /etc/os-release
bm_version
free -h
df -hT
```

OTA 脚本实际使用 `/proc/cpuinfo` 判断芯片，必须确认输出为 `bm1684x`：

```bash
awk -F': ' '/model name/{print $2; exit}' /proc/cpuinfo
```

预期：

```text
bm1684x
```

某些 BM1684X BSP 中 `/proc/device-tree/model` 不存在，且 `compatible` 可能显示 `linux,dummy-virt`。这不能代替芯片检查，也不表示设备一定是虚拟机；以 `bm_version`、`/proc/cpuinfo` 和启动固件信息为准。

### 3.2 确认 eMMC 和挂载状态

不同旧固件的 `lsblk -o` 支持字段不同，优先使用兼容性更好的命令：

```bash
lsblk
sudo blkid
sudo fdisk -l /dev/mmcblk0
df -hT /data
```

实测设备的最后一个分区是 `/dev/mmcblk0p7`，挂载到 `/data`。如果另一台机器不是这种布局，不要直接套用本流程。

### 3.3 确认 OTA 所需工具

```bash
for tool in systemd-run tee bc gdisk mkimage awk sed tr gzip dd sgdisk fdisk fuser wall head; do
  command -v "$tool" >/dev/null 2>&1 || echo "MISSING: $tool"
done
```

没有任何 `MISSING` 输出才能继续。

### 3.4 准备恢复条件

- 使用稳定电源，升级期间禁止断电。
- 建议准备串口，常用参数为 `115200 8N1`。
- 记录当前 IP、网卡信息和 SSH 登录方式。
- 确认局域网中有另一台机器用于保存备份和 SDK 包。

## 4. 备份并复制到另一台机器

以下示例的备份服务器为 `dxc@172.16.20.193`，请按实际环境修改。

### 4.1 备份系统信息

```bash
mkdir -p /data/backup-v23-sp5

sudo tar czf /data/backup-v23-sp5/boot-net-sdk.tgz \
  /boot \
  /etc/netplan \
  /etc/profile \
  /etc/profile.d \
  /opt/sophon

bm_version > /data/backup-v23-sp5/bm-version.txt
sudo blkid > /data/backup-v23-sp5/blkid.txt
dpkg -l | grep -E 'sophon|opencv|ffmpeg|sail' \
  > /data/backup-v23-sp5/sophon-packages.txt
ip -br addr > /data/backup-v23-sp5/ip-addresses.txt
ip link > /data/backup-v23-sp5/network-links.txt
```

`tar: Removing leading '/'` 是正常提示。

### 4.2 备份业务数据和登录配置

先停止 Docker，避免备份过程中数据变化：

```bash
sudo systemctl stop docker
```

根据设备中实际存在的目录调整下面的列表：

```bash
sudo tar --xattrs --acls --numeric-owner \
  -czf /data/backup-v23-sp5/data-extra.tgz \
  -C /data docker ota soc_aging tmp

sudo tar --xattrs --acls --numeric-owner \
  -czf /data/backup-v23-sp5/system-extra.tgz \
  /home/linaro /etc/ssh /etc/systemd/system

sudo chown linaro:linaro /data/backup-v23-sp5/*.tgz
```

全量模式会重建 rootfs 和 `/data`。如果设备上还有自定义程序、systemd 服务、定时任务、证书或密钥，也应单独加入备份。

### 4.3 生成校验文件并复制到异机

```bash
cd /data/backup-v23-sp5

sha256sum \
  boot-net-sdk.tgz \
  data-extra.tgz \
  system-extra.tgz \
  *.txt > SHA256SUMS

scp -r /data/backup-v23-sp5/ \
  dxc@172.16.20.193:/mnt/dxc/sophon/backup-v23-sp5/
```

登录备份服务器，找到 `SHA256SUMS` 所在的实际目录并验证：

```bash
cd /mnt/dxc/sophon/backup-v23-sp5
sha256sum -c SHA256SUMS
```

必须全部显示 `OK`。如果 `scp -r` 生成了嵌套目录，先使用以下命令定位：

```bash
find /mnt/dxc/sophon/backup-v23-sp5 -maxdepth 2 -type f
```

## 5. 准备 SDK v26.03.01 升级包

完整文件名：

```text
SDK-26.03.01.zip
```

完整 SDK ZIP 约 20GB，不建议传到盒子。先在 PC 或 Linux 服务器解压，只把以下文件传到设备：

```text
release/sophon-img_20260414_154148/sdcard.tgz
```

实测该文件约 971MB，MD5 为：

```text
bb35f0305f551b196ee5b3b13bcf1529  sdcard.tgz
```

该外层 MD5 只适用于本文实测包；最终仍必须以包内 `md5.txt` 的逐文件校验结果为准。

从服务器传到盒子：

```bash
mkdir -p /data/upgrade-v26

scp dxc@172.16.20.193:/mnt/dxc/sophon/release/sophon-img_20260414_154148/sdcard.tgz \
  /data/upgrade-v26/
```

检查空间和外层文件：

```bash
cd /data/upgrade-v26
df -h /data
ls -lh sdcard.tgz
md5sum sdcard.tgz
tar tzf sdcard.tgz | head -60
```

解压并校验包内所有文件：

```bash
mkdir -p /data/upgrade-v26/package
tar xzf sdcard.tgz -C /data/upgrade-v26/package

cd /data/upgrade-v26/package/sdcard
md5sum -c md5.txt
```

必须全部为 `OK`。如果在 `/data/upgrade-v26` 直接运行 `md5sum -c md5.txt`，会因为目录错误而找不到文件；正确工作目录是 `package/sdcard`。

## 6. 选择是否保留 `/data`

这是整个流程中最重要的判断。

### 6.1 查看当前 DATA 分区起始扇区

```bash
sudo fdisk -l /dev/mmcblk0 | grep '^/dev/mmcblk0p7'
```

本文使用的 v26.03.01 升级包中，新 DATA 分区起始扇区为：

```text
28602368
```

实测旧 v23.09 LTS-SP5 设备的 DATA 起始扇区为：

```text
29564928
```

两者相差 `962560` 个 512 字节扇区，即 470MiB。因此该设备不能使用默认的“保留最后分区”模式。

### 6.2 情况 A：起始扇区完全相同

如果当前最后分区与新包的起始扇区相同，可以使用默认模式：

```bash
cd /data/upgrade-v26/package/sdcard
sudo bash ota_update.sh
```

默认模式会启用 `LAST_PART_NOT_FLASH`，保留最后一个 `/data` 分区。

### 6.3 情况 B：起始扇区不同

默认模式会安全中止并显示类似错误：

```text
[PANIC] LAST_PART_NOT_FLASH mode, check last part start [28602368] != [29564928]
```

该检查发生在缩小 `/data`、写入 eMMC 和替换启动脚本之前。此时 SSH 不会断开，设备也不会重启。

确认异机备份全部校验成功后，使用全量模式：

```bash
cd /data/upgrade-v26/package/sdcard
sudo bash ota_update.sh LAST_PART_NOT_FLASH=0
```

启动后的日志必须出现：

```text
[INFO] LAST_PART_NOT_FLASH mode disable
```

该模式会清空并重建 `/data`。虽然升级包本身位于 `/data`，官方脚本会先把刷机所需内容写入 eMMC 尾部，再重启进入 U-Boot 刷写阶段。

## 7. 监控 OTA

`ota_update.sh` 会通过 `systemd-run` 启动后台任务，然后立即返回命令提示符。这是正常行为，不代表已经完成。

启动输出应包含：

```text
Running as unit: sophon-ota-update.service
Active: active (running)
```

立即离开 `/data` 并查看日志：

```bash
cd /
sudo tail -f /dev/shm/ota_shell.sh.log
```

也可以查看服务状态：

```bash
sudo systemctl status sophon-ota-update.service --no-page -l
```

标志文件：

```text
/dev/shm/ota_success_flag    Linux 升级准备完成
/dev/shm/ota_error_flag      Linux 升级准备失败
```

`ota_success_flag` 只表示升级包暂存完成。随后设备会自动重启，U-Boot 才开始真正刷写各分区；此时仍然不能断电。

脚本会停止 Docker、结束占用 `/data` 的进程并卸载 `/data`，所以 SSH 断开是正常现象。建议等待 10～15 分钟，直到设备重新能够登录。

## 8. 失败处理

如果日志出现 `[PANIC]`：

1. 按 `Ctrl+C` 退出 `tail -f`。这只会停止日志查看。
2. 不要重复运行 OTA，也不要改用 `LAST_PART_NOT_FLASH=0` 试错。
3. 执行：

```bash
cd /
systemctl is-active sophon-ota-update.service
ls -l /dev/shm/ota_error_flag /dev/shm/ota_success_flag 2>/dev/null
df -hT /data
ls -lah /data/upgrade-v26/package/sdcard/gpt.gz*
sudo tail -n 200 /dev/shm/ota_shell.sh.log
```

本文实测的分区起始点不一致错误中，结果是：

- 服务变为 `inactive`；
- 只有 `ota_error_flag`；
- `/data` 仍正常挂载；
- 没有遗留 `gpt.gz.ota_update_bak`；
- 系统和 eMMC 尚未被修改。

其他错误发生的阶段可能不同，不能一概认为安全。应保存完整日志后再判断。

## 9. 升级后验证

设备重新上线后，不必再次手动执行 `source /etc/profile`；新的 SSH 登录已经加载环境。重复加载时可能出现以下无害提示：

```text
-bash: PROMPT_COMMAND: readonly variable
```

验证固件：

```bash
bm_version
uname -a
df -hT
free -h
dpkg -l | grep -E 'sophon|opencv|ffmpeg|sail'
which ffmpeg
ffmpeg -version | head -10
```

本次成功结果的核心版本：

```text
SophonSDK version: v26.03.01
sophon-soc-libsophon : 0.5.3
sophon-soc-libsophon-dev : 0.5.3
sophon-mw-soc-sophon-ffmpeg : 0.15.0
sophon-mw-soc-sophon-opencv : 0.15.0
```

全量模式升级后 `/data` 约 44GB 且基本为空，这是预期结果。

检查 Python 运行时：

```bash
python3 - <<'PY'
import sys
print("python:", sys.version)

for module in ("numpy", "cv2", "sophon.sail"):
    try:
        loaded = __import__(module, fromlist=["*"])
        print(module, "OK", getattr(loaded, "__version__", "unknown"), loaded.__file__)
    except Exception as exc:
        print(module, "ERROR", repr(exc))
PY
```

本次镜像的实测结果：

```text
Python 3.8.10
NumPy 1.24.4
cv2: 初始为 ModuleNotFoundError；配置 SDK 自带绑定路径后为 OpenCV 4.1.0
sophon.sail: ModuleNotFoundError
FFmpeg: 4.1.3-sophon-0.15.0
```

这不表示 SDK 刷写失败。SoC 镜像已安装 Sophon OpenCV/FFmpeg 的系统运行库，但没有自动把 OpenCV Python 绑定加入模块搜索路径，SAIL Python 包也没有随镜像安装。

实测 OpenCV 绑定位于：

```text
/opt/sophon/sophon-opencv-latest/opencv-python/cv2.so
```

临时配置和验证：

```bash
export PYTHONPATH=/opt/sophon/sophon-opencv-latest/opencv-python${PYTHONPATH:+:$PYTHONPATH}

python3 - <<'PY'
import cv2
print("opencv:", cv2.__version__)
print("cv2 file:", cv2.__file__)
PY
```

实测输出：

```text
opencv: 4.1.0
cv2 file: /opt/sophon/sophon-opencv-latest/opencv-python/cv2.so
```

不要使用 PyPI 的普通 `opencv-python` 覆盖该文件。交互式 shell 和 systemd 服务需要分别配置此 `PYTHONPATH`；systemd 不会自动读取用户的 `.bashrc`。

## 10. 升级后的恢复边界

只选择性恢复：

- 项目代码和模型；
- SSH 公钥；
- 确认仍适用于新系统的网络配置；
- 自定义 systemd 服务；
- 必要的业务数据。

不要覆盖恢复：

- `/boot`；
- 旧版 `/opt/sophon`；
- 旧版 libsophon、FFmpeg、OpenCV；
- 整个 `/etc` 或整个 rootfs。

旧 SDK 文件保留在备份中仅用于审计和必要时人工提取，不能覆盖 v26.03.01 的运行库。

## 11. 后续应用环境

固件升级与 Python 推理环境安装是两个阶段。完成本文后，还需要：

1. 配置 Sophon OpenCV 0.15.0 的 Python 绑定路径；
2. 安装与 SDK v26.03.01 匹配、包含多媒体接口的 SAIL；
3. 对本项目建议使用 SAIL v3.11.1，因为该版本明确支持 BM1684X SDK v26.03.01，并修复了 `MultiDecoder`、`BMImage.asnumpy` 等内存泄漏；
4. 验证 `Handle`、`Engine`、`BMImage`、`Bmcv`、`MultiDecoder` 和 `BMImage.asmat`；
5. 再部署 RTSP 检测项目和 BModel。

SAIL 必须包含多媒体模块，不能使用 `ONLY_RUNTIME=ON` 构建，否则项目需要的 Decoder、MultiDecoder 和 BMCV 接口不可用。

本次匹配 SDK v26.03.01 的 SAIL v3.11.1 构建与验证过程已单独记录在 [SAIL v3.11.1 面向 BM1684X SDK v26.03.01 的交叉编译记录](SAIL_3.11.1_BM1684X_SDK_26.03.01_CROSS_COMPILE.md)。

完整 SDK 中实测包含以下 SAIL 文件，但仅凭文件名还不能判断源码包内是否带可直接安装的 SoC wheel：

